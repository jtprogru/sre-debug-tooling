# JVM перестала отвечать

> **TL;DR:** `jattach <pid> threaddump` из эфемерного контейнера с `--target`. Нужны PID namespace таргета и `SYS_PTRACE`, рестартовать при этом ничего не надо.

## Когда применять

Java-сервис поднят, процесс жив, а отвечать перестал: health-check по таймауту, треды выглядят залипшими, или CPU в сотке при нулевой полезной работе.

Не рестартуй первым делом. Рестарт уничтожает единственную улику, которая это объясняет.

## Быстрая диагностика

Цепляйся с PID namespace таргета и привилегиями, достаточными, чтобы аттачиться к чужому процессу:

```bash
kubectl debug -n <namespace> <pod> -it \
  --image=ghcr.io/jtprogru/sre-debug-tooling:full-latest \
  --target=<container> \
  --custom=deploy/profile-sysadmin.yaml -- bash
```

Найди JVM и сними thread dump:

```bash
ps aux | grep -m1 '[j]ava'
jattach <pid> threaddump > /tmp/threads.txt
head -50 /tmp/threads.txt
```

Heap и состояние GC:

```bash
jattach <pid> jcmd GC.heap_info
jattach <pid> jcmd VM.flags
```

## Что означают ответы

`ps` не показывает java-процесс — ты забыл `--target` и смотришь в собственный PID namespace debug-контейнера. Самая частая ошибка в этом сценарии.

Много тредов `BLOCKED` на одном мониторе — контеншен на локе. Стек в верхушке заблокированной группы называет лок.

Много тредов `WAITING` на пуле соединений — пул исчерпан, а настоящая проблема ниже по стеку. Бери латентность зависимости, а не JVM.

Треды в `RUNNABLE` на чтении из сокета — JVM ждёт сеть и вообще не висит.

`GC.heap_info` показывает забитый old gen и высокий GC time — JVM жива и тратит всю себя на сборку. Сверь с memory limit контейнера, прежде чем объявлять это утечкой.

## Как вытащить heap dump

Heap dump останавливает JVM на время снятия и может весить гигабайты. Делай, когда решил, что диагноз стоит паузы:

```bash
jattach <pid> dumpheap /tmp/heap.hprof
ls -lh /tmp/heap.hprof
```

`kubectl cp` не работает с эфемерными контейнерами, так что копируй через файловую систему таргета или сразу пиши дамп на смонтированный том.

## Митигация

Когда thread dump на руках, рестарт становится нормальной митигацией — улика уже собрана. Если исчерпан пул соединений, его расширение прячет проблему ниже по стеку ровно на то время, за которое пул наберётся снова.

## Root cause

Зависимость перестала отвечать, а у клиента нет таймаута. `synchronized` на горячем пути. Heap, выставленный выше memory limit контейнера: ядро прибивает JVM по OOM раньше, чем она успевает бросить `OutOfMemoryError`.
